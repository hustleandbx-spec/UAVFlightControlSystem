## 1. 目的与范围

- 本文件承载**子系统需求**：把系统需求（SYS-REQ-001..022）从顶至下分配到各模块，回答"**每个模块各自要满足什么**"。与 07（系统级需求规格）同级、低一层。
- 模块集（DEC-074）：**Gateway / Commander / MissionManager / Navigator（制导）/ FlightControl / StateEstimation / Logging**；FailSafe 与参数系统实现后置（TBD-003/014/015），第一阶段不写其 SUBSYS-REQ。
- **A3 守则（DEC-091/111）**：第一阶段纯正常流，凡根因=异常的处置需求一律标"实现后置（FailSafe）"，不逐模块展开。

## 2. 追溯纪律与实现形式

追溯 = **双向过程**、产物为矩阵（标准依据：ARP4754B §5.4.6.1 双向追溯；ISO 29148 §6.5.2.3 验证交叉引用矩阵 VCRM）。实现分三种形式：

- **① 行内两向**（本文档各需求表）：每条需求记录 `来源（↑父需求/决策）` 与 `验证（↓VER）`，设计归属 = 模块本身（前缀隐含）。这是追溯的本体。
- **② SYS↔SUBSYS 映射表**（§3）：从各表来源列逆向后拼装，回答"每条父需求是否被子需求覆盖"（ARP4754B 自顶向下半边）。
- **③ 端到端追溯矩阵（VCRM）**（13_V&V_Plan）：逐条闭合"需求 → 设计 → VER → 结果"，执行时填 PASS/FAIL（29148 §6.5.2.3）。

端到端链 `SN→MOE→MOP→SYS-REQ→SUBSYS-REQ→DESIGN/MODEL→VER→TEST` 不逐行复述，由 13 矩阵统一核查（孤儿需求 / 未验证需求 / 悬空追溯在此暴露）。

## 11. 维护规则

- **来源纪律**：每条 SUBSYS-REQ 的来源列必须指向存在的 SYS-REQ/DEC（自底向上可追溯）；新增需求先有来源再入档。
