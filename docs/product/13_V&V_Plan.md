## 1. 目的与范围

- **验证（Verification）** = "按规定把系统做对了"；**确认（Validation）** = "系统是否满足实际任务需要"。两者分离。
- **第一阶段 = MIL + SIL 两级纯仿真验证**（DEC-033/114）；**HIL 与实机 Validation（TBD-001）后置第二阶段**（DEC-114）。
- 验证对象 = SYS-REQ-001..022（07）+ SUBSYS-REQ（14）；顶层判定依据 = MOE-A/B + 安全门（06）。
- 第一阶段纯正常流（DEC-111）：异常处置相关需求（SYS-REQ-012/013/014a 等）的验证随异常工作包后置。

## 2. 验证策略

### 2.1 级别

| 级别 | 内容 | 验证什么 | DO-331 锚定 |
|---|---|---|---|
| **MIL**（模型在环） | Simulink 模型级 | 算法/逻辑/接口正确性、段推进、命令审查、判据判定 | MB.6.8 Model Simulation（模型仿真验证模型） |
| **SIL**（软件在环） | 代码生成后 | 生成软件行为与模型一致、时序/周期符合分析值 | MB.6.4 Software Testing（需求基测试于生成软件）+ MB.6.3 评审/分析 |

### 2.2 验证方法（ARP4754B §5.5.5 四法）

| 方法 | 说明 | 本项目用法 |
|---|---|---|
| 检查/评审（Inspection/Review） | 文档/数据核对 | 规划层保证、控制分析评审、接口评审 |
| 分析（Analysis，含 Modeling / Coverage Analysis） | 详细考察实现满足需求 | 实时性分析（VER-022）、覆盖率分析 |
| 测试/演示（Testing/Demonstration） | 运行/演示证明满足需求 | **绝大多数 VER（MIL/SIL 仿真）** |
| 相似性/服役经验（Similarity/Service Experience） | 借用既往数据 | 第一阶段不适用（无服役经验） |

- 工具：Simulink Test / MATLAB 测试框架（`test_minimal` / `add_test_suites`）；SIL = 生成软件运行 + 时序采集。
- 覆盖率：MIL/SIL 需求覆盖率 = DO-331 MB.6.7（Model Coverage Analysis）；追溯覆盖 = VCRM（§8）。

### 2.3 验证环境（DEC-117..120，2026-08-12 落地）

> 验证环境 = **单一仿真环境**（DEC-117），由 ① plant 基线（2.3.1）② 验证 GCS 工具链（2.3.2）③ 场景编排与注入位（2.3.3）④ 数据记录与可复现（2.3.4）四部分构成。本节回答"在哪验证、用什么驱动、怎么注入、如何留证"。

#### 2.3.1 plant 基线（DEC-117 + DEC-122）

- **基线** = 现有/在建 6-DOF 动力学模型 + 传感器模型（RTK/IMU/气压）+ 动力系统；**单一环境**（不另开双环境、不分档）；fidelity 不需实物匹配（DEC-033/114）。
- **前提假设（R-02）**：现有 plant 可稳定飞完参考架次五段（VER-010 前提）。**早期验证**：VER-010 雏形（门审查通过 → 起飞 → 出航 → 任务 → 返航 → 降落 → 触地）最先跑通，验证 plant 能力；失败 → R-02 触发（额外 plant 工作，见 process/02）。
- **fidelity 触发机制（DEC-122，需要性驱动）**——逐步增强的触发 = 需要性驱动，非"越丰富越好"：

| 触发源 | 需要的判据/分析 | 需要的 plant 特征 | 触发条件 |
|---|---|---|---|
| VER-021 触地判据 | 旋翼卸载/推力低门限（DEC-100 判据②） | 动力系统产生与指令非单调静态的卸载信号（触地载荷被地面支撑 → 转速/电流/推力特征变化） | VER-021 排程前若基线动力模型仅"推力随指令单调" → 增强动力 fidelity |
| 数值回填（DEC-056） | 段间跟随误差 / 能源裕度 / 控制周期延迟 | 执行机构 10~30ms 延迟与动态特性、能源/续航模型 | 控制分析回填前若基线为理想执行机构/静态推力 → 增强至能支撑分析 |
| VER-010 全流程 | 五段稳定飞行（R-02 前提） | 飞行动力学完整性（悬停/机动/起降） | R-02 早期验证失败 → 修复/增强 plant |

- **增强原则**：① **最小充分度**（恰好支撑该判据/分析）；② 每次增强记下方 fidelity 变化记录表（可追溯）；③ 增强不改单一环境、不回退既有 VER 基线——受影响 VER 标记重跑。

#### 2.3.2 验证 GCS 工具链（DEC-118）

- 开发期地面站 = **MAVProxy**（快速全流程仿真、脚本化自动化验证）；功能成熟后转 **QGC** 正式地面站。
- 注入方式 = 命令/计划经**真实 MAVLink**（MAVProxy/QGC → Gateway 在环 → FC），**非总线直注**（DEC-118）；Gateway 在环覆盖子协议状态机（命令/FTP/Time Sync，DEC-112）。
- **R-03 风险验证（MAVProxy FTP 子协议）**：自研富语义计划经 MAVLink FTP 上传（DEC-016），MAVProxy FTP 子协议成熟度需早期验证（R-03）——**VER-001 排程前**先跑 FTP 雏形（MAVProxy 端真实 FTP 上传 → Gateway → MM 解析+结构校验 → MissionPlanAvailableBus 通知）；失败 → 切换 QGC 承担计划上传（R-03 缓解，process/02）。

#### 2.3.3 场景编排与注入位（DEC-119）

- **混合编排**：自动化跑批 = 脚本（MAVProxy 脚本 + 场景配置，对应"快速全流程仿真"定位）；人工/单条调试 = Simulink Test（4_Test 框架）。两者共享同一套注入位定义。
- **注入位能力清单**（DEC-119 三类；命令/计划注入经真实 MAVLink + Gateway 在环，状态条件/plant 条件/观察位为验证环境内部测试手段）：

| 注入位类别 | 载体/信号 | 覆盖的 VER |
|---|---|---|
| 计划注入（数据通道） | MissionPlanBus / FTP 上传接口：非法计划（不可解析/字段非法/容量>400/末航点非停/段结构非法）、含绕行/停过/偏航航线、无返航航点 | VER-001/015/017/018/019 |
| 命令注入（指令通道） | CommanderRequestBus：开始任务、模式级命令（返航/降落/悬停）、接管、解锁/加锁、go-to-point 激活 | VER-002..009/011/014 |
| 状态条件注入 | 各模块状态流覆盖（SE Status=错误、GcsLinkStatusBus=断开、MissionPlanAvailableBus=不可用）；传感器信号（RTK 无效、传感器健康异常）；配置（围栏无效/动力未就绪/能源不足） | VER-003..008/009（7 门组合） |
| plant 条件注入 | DynamicModelBus / plant 参数 / 物理场景文件（近地触地、风扰动、能源消耗） | VER-005/010/020/021/022 |
| 观察/采集位 | 总线信号订阅（执行日志、轨迹记录、MOE 判定输入、触地候选信号） | VER-010/021/022（SIL 时序） |

> 说明：DEC-118"非总线直注"约束的是**命令/计划**注入路径（走真实 MAVLink，验证协议层）；状态条件/plant 条件/观察位属验证环境内部测试手段，两者不矛盾。

#### 2.3.4 数据记录与可复现（DEC-120）

- 每次 VER 运行自动落原始数据：执行日志（LOG-001/002）+ 轨迹 + MOE 判定表 + 模型/数据字典/场景版本 + 测试配置（含 seed）。
- MOE **自动初判**（脚本）；**关键项人工复核**（VER-010 全流程、VER-021 触地判定）后入 VCRM（§8）。
- 可复现 = 版本（模型/字典/场景）/seed 逐次标记；时间戳与 Time Sync 对齐（DEC-112/090）。

## 4. 集成验证场景

### VER-010 参考架次全流程（集成用例，MIL + SIL，2026-08-08 确认）

**被验证需求：** SYS-REQ-010（自主执行全流程）+ 串联 VER-001/002..009/014/015/017/018/019/020/021；判定 = MOE-A/B + 安全门。

| 项 | 内容 |
|---|---|
| **场景** | 电力设施巡检参考架次（出航 ≤1km、任务区片状+带状、末航点=停）：解锁 → "开始任务" → 全程自主（起飞→出航→任务区→返航→降落→触地）→ 正常终止 |
| **前置** | 计划结构校验通过（VER-001）；起飞门全绿（SYS-REQ-002..008）；链路接通 |
| **步骤** | ① 上传计划 → 校验通过（PlanAvailable=true）→ ② 解锁（基础武装检查）→ ③ "开始任务"→ 7 门审查通过 → 批准 → ④ 离地爬升至安全起飞高度（SYS-REQ-014）→ ⑤ 出航至首航点（015）→ ⑥ 任务区航点按序执行：停点到达判据推进 / 过点曲线穿越 / 偏航按航点模式（017/018）→ ⑦ 末航点完成 → 返航至 home（019）→ ⑧ home 上方垂直下降、近地减速、触地（020/021）→ ⑨ 触地 → 电机停转+加锁+上报任务结束（DEC-042） |
| **通过判据** | MOE-A：完整执行五段、航点按序、正常终止（执行日志判定）；MOE-B：停/过/偏航飞行级动作按计划执行；安全门：全程无包线/围栏违反 |
| **级别** | MIL → SIL，两级各跑一遍 |
| **数据来源** | 执行日志（LOG-001/002）、MOE-A/B 判定表、Test Manager 结果 |

**设计说明：** 全流程闭环最终判定——所有模块首次串联跑通，任何模块间接口断裂、段推进错误、命令时序错乱在此暴露。通过 → 系统"能做对的事"；其余 VER-001..009/014..021 = 逐条拆解与故障注入。

## 7. 确认（Validation）策略（2026-08-12 推理链具体化）

- **后置**：实机 Validation（TBD-001，第二阶段）；HIL（DEC-114，第二阶段）。
- **第一阶段 = 间接确认**（推理链占位，禁止把仿真当实机确认）——**间接确认推理链**（DEC-010/017）：
  - **前提 P**：FlightCore 完整自主执行参考架次（起飞→出航→任务→返航→降落→触地正常终止 + 全程安全包线内）是"巡检任务有效性"的必要前提。第一阶段无载荷（DEC-009），MOE-A/B 为**飞行执行代理** MOE（06）。
  - **链① 执行前提闭合**：VER-010 全流程 PASS（MOE-A：五段完整 + 正常终止；安全门：全程无包线/围栏违反）⇒ 前提 P 成立。
  - **链② 按计划分量闭合**：MOE-B 动作执行完整度 PASS（停/过/偏航按计划执行）⇒ P 的"按计划"分量达成。
  - **结论**：第一阶段确认证据 = VER-010 全流程 PASS + MOE-A/B 判定表（链①②闭合）。**只闭合"执行前提"，不闭合"任务有效性本身"**。
- **直接确认（第二阶段后置）**：真机 + 载荷（三轴光电吊舱，DEC-009）→ 数据覆盖/缺陷识别等任务 MOE → 依赖 TBD-001（实机）。
- **测量 vs 闭合**：MOE-C（自主性）/MOE-D（计划保真度）第一阶段测量（VER-011/MOP），但不作为间接确认闭合判据（闭合 = MOE-A/B + 安全门，06）。
- **边界声明**：① 仿真 PASS ≠ 实机确认（DEC-033/114 第一阶段纯 MIL/SIL）；② 第一阶段全部活动本质 = Verification（按 07/14 需求做对）；③ 间接确认是"前提闭合"逻辑、非实证——实证（真机满足实际任务需要）随实机后置。
