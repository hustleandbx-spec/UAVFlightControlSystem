## 1. 项目愿景

本项目旨在研制一套面向工业无人机应用、能够长期演进并具备真实工程落地可能的自主 FlightCore 系统。

项目不以复刻现有开源飞控功能或单纯验证某种控制算法为目标，而是建立一条完整、可追溯、可验证的飞控工程链，使需求、架构、模型、算法、软件和验证活动之间形成明确关系。

项目最终应覆盖：

**任务与需求定义 → 系统架构 → 飞行动力学建模 → 状态估计 → 制导与控制 → 控制分配 → 执行机构 → 软件实现 → MIL → SIL → HIL → 实机试飞 → 需求验证与迭代。**

项目首先以大型工业四旋翼作为 Reference Vehicle，在此基础上逐步建立支持复合翼、倾转旋翼以及更高级自主飞行能力的演进基础。

## 2. 项目定位

### 2.1 工程定位

项目按照真实飞控产品的工程逻辑进行建设。每一个重要设计决策应能够回答：

- 它来自什么任务或系统需要；
- 它受到什么工程约束；
- 为什么选择当前设计；
- 如何证明设计满足要求；
- 如何从模型验证逐步迁移到真实硬件和实机。

“能够仿真飞行”不作为项目最终完成标准，模型、算法和软件实现均应具备向真实系统迁移的可能性。

### 2.2 技术定位

项目追求技术先进性，但不以堆叠 PID、LQR、MPC、NMPC、RL 等算法作为先进性的判断标准。

技术先进性主要体现在：

1. **控制能力**：能够应对约束、扰动、参数变化、非线性和构型演进；
2. **工程方法**：需求可追溯、模型化设计、自动化验证、参数管理、代码生成以及 MIL/SIL/HIL 连续验证；
3. **系统架构**：飞行器构型、控制算法、状态估计和上层自主系统之间具有清晰边界；
4. **演进能力**：当前四旋翼实现不得无必要地封死未来复合翼、倾转旋翼、GNSS-denied 和自主规划能力的扩展路径。

## 3. 当前 Reference Vehicle

### 3.1 RV-Q01：大型工业四旋翼

当前 Reference Vehicle 定位为与 DJI Matrice 400 相近量级的大型工业四旋翼，但项目不以复制 Matrice 400 的产品指标和实现方式为目标。

当前仅确定量级和应用定位，具体质量、惯量、几何尺寸、动力系统、载荷范围及性能包线将在后续 Vehicle Definition 中形成正式参数基线。

### 3.2 当前应用方向

- 主要面向工业无人机应用；
- 当前候选任务为工业巡检、观测/侦察；
- 优先考虑户外环境；
- 初期允许依赖 GNSS/RTK；
- 后续考虑 GNSS-denied 环境；
- 第一阶段暂不将系统故障和容错控制作为主要设计对象。

### 3.3 当前性能价值取向

性能目标不采用全任务阶段统一排序，而应根据任务阶段变化：

- **任务区域：安全优先，其次任务精度；**
- **出航阶段：在满足安全约束的前提下，更重视飞行效率和能耗；**
- **任何阶段：保持飞行器可控以及满足规定安全约束，高于任务完成度和效率目标。**

## 4. 当前系统级目标（v0.1）

以下目标为当前项目愿景的一部分，状态均为 Draft，后续必须通过 ConOps、MOE/MOP 和系统需求分析继续细化。

### SYS-GOAL-01 自主任务执行

FlightCore 应支持工业无人机自主完成起飞、出航、任务航迹执行、返航和降落的完整正常飞行过程，同时允许操作者监督并在必要时取得飞行控制权。

### SYS-GOAL-02 安全约束飞行

在定义的正常工作条件和飞行包线内，系统应保持飞机处于可控状态，并使安全约束具有高于任务性能和运行效率的优先级。

### SYS-GOAL-03 高品质精确飞行

在任务作业阶段，FlightCore 应提供足够的轨迹跟踪、位置保持、姿态稳定和扰动抑制能力，以支持工业巡检及观测类任务。

### SYS-GOAL-04 阶段相关的飞行品质

系统应能够根据飞行阶段采用不同的性能目标：出航阶段强调效率，任务区域强调安全与精度，而非全程追求同一种控制品质。

### SYS-GOAL-05 载荷适应能力

在规定的重量、质心和惯量工作包线内，合法任务载荷变化不应要求操作者针对每种载荷重新进行控制律标定。

本目标不预先规定必须采用在线参数辨识、自适应控制、增益调度或其他特定技术方案。

### SYS-GOAL-06 能源约束任务管理

系统应将能源安全裕度纳入任务执行决策，并支持任务安全中断、返航以及后续任务续接。

### SYS-GOAL-07 架构演进能力

系统以大型工业四旋翼作为首个 Reference Vehicle，同时应在架构设计上保留向复合翼、倾转旋翼、GNSS-denied 以及更高级自主规划能力演进的合理边界。

## 5. 当前正常任务概念（ConOps 雏形）

当前以工业设施巡检作为 Reference Mission，用于发现和推导系统需要，但不将其永久限定为 FlightCore 的唯一应用场景。

正常任务过程暂定为：

1. 操作者完成任务载荷安装和任务航线规划；
2. FlightCore 完成任务准备并进入自主飞行；
3. 飞机柔和离地，平滑建立爬升速度；
4. 飞机以效率为主要目标完成至任务区域的出航；
5. 进入任务区域后，提高安全和任务精度的优先级；
6. 当前采用预规划任务航线，航点语义由任务层定义，Guidance 负责形成可执行的轨迹/设定值；
7. 在线环境感知负责支持实际飞行中的障碍物安全约束，任务精度与安全发生冲突时任务要求退让；
8. 当剩余能源不足以在规定安全裕度下继续完成任务时，允许中断任务并返航；
9. 保存有效任务进度，使后续架次能够合理续接未完成任务；
10. 返航后到达降落区域上空，稳定垂直下降，近地减速并平稳接地。

## 6. 已确认的关键设计思想

### 6.1 FlightCore 与具体飞行器解耦

FlightCore 不等同于某一具体四旋翼。四旋翼是当前首个 Reference Vehicle，具体飞行器的物理参数、构型及执行机构特征应通过明确的 Vehicle Definition 与通用飞控能力连接。

### 6.2 Mission、Guidance、Safety 与 Control 职责分离

当前认识为：

- Mission 表达任务意图和航点语义；
- Guidance 将任务意图转化为飞行器可执行的轨迹或设定值；
- Safety / Constraint 机制负责施加环境与飞行包线相关约束；
- Control Law 负责实现经过约束后的可执行运动目标。

不得默认所有 Position Setpoint 都必须由全球 GNSS 坐标表达。未来近场任务、视觉导航和 GNSS-denied 场景可能需要基于局部环境或任务目标的相对参考。

### 6.3 当前自主能力边界

当前实现采用**预规划任务航线 + 在线安全修正**作为主要方案。

未来可接入基于 SLAM、局部规划、视觉/激光感知乃至更高级智能模型的自主任务规划能力，但当前阶段不要求实现。系统架构只需避免无必要地阻断这类演进。

## 7. 当前明确不纳入第一阶段的内容

- 系统级故障容错设计；
- 单电机/多电机故障控制；
- GNSS-denied 的正式实现；
- VLA/VLN 自主任务规划；
- 复合翼和倾转旋翼的实际控制律实现。

以上内容属于未来演进方向，不代表永久排除。

## 8. 待确定事项（TBD）

当前不人为给出尚无来源的性能数字。以下内容需要通过后续任务分析、Vehicle Definition、MOE/MOP 推导得到：

- Reference Vehicle 的正式质量范围与最大起飞重量；
- 任务载荷范围；
- 允许的质心范围；
- 三轴惯量及变化范围；
- 飞行速度、加速度、角速度和姿态工作包线；
- 风场及其他环境工作包线；
- 起飞、出航、巡检、悬停、返航和降落的定量性能指标；
- 位置、速度、姿态、角速度等控制精度指标；
- 扰动抑制与恢复性能；
- 能源安全裕度；
- 障碍物安全距离及其适用场景；
- 各阶段实时性、控制周期和时延要求。

这些 TBD 在获得明确任务来源或工程依据之前不得任意填充为“正式指标”。

## 9. 后续需求演进关系

当前预期的需求生成链为：

**Project Vision → Stakeholder Needs → ConOps → MOE → MOP → System Requirements → Subsystem Requirements → Architecture / Design → Verification & Validation。**

下一阶段应优先回答“如何判断七项系统级目标已经实现”，据此建立项目第一版 MOE，而不是直接进入控制律参数或算法选择。
